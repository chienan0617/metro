# 1. 遊戲願景與定位

## 1.1 核心概念

這是一款以大型區域地圖為舞台的軌道交通經營遊戲。地圖不是一座城市的單一街區，而是一個包含**許多彼此分離、規模不同、需求不同的城市**的完整區域。

玩家經營一家交通公司，從少量資金和一座起始城市出發，逐步連接周邊城市。玩家可以自行決定：

- 哪些城市要先連接。
- 一條路線要經過哪些城市。
- 哪些城市設為停靠站、哪些只作為經過區域。
- 何處設置轉乘樞紐。
- 哪些路線需要增加班次或更換高容量列車。
- 如何在建設成本、乘客需求、行車時間與營運收益之間取得平衡。

遊戲的主要樂趣是**親手把零散城市逐步連成一個有效率的交通網絡**。列車收集和公司升級是支援系統，不能取代路線規劃本身。

## 1.2 類型

- 交通網絡建設
- 模擬經營／Tycoon
- 路線規劃與資源管理
- 列車收集與升級
- 任務／章節進程

## 1.3 設計原則

1. **地圖優先**：地圖是主要遊戲場景，不是附屬的小視窗。
2. **路線由玩家決定**：不能只讓玩家按下「自動建立最佳路線」就完成主要玩法。
3. **城市各有價值**：人口、產業、旅遊、地形和交通需求應有差異。
4. **結果可理解**：玩家必須知道一條路線為什麼賺錢或虧損。
5. **簡單操作、深度決策**：操作不應複雜到需要手動駕駛每一列車，但建設與經營要有策略性。
6. **可持續擴充**：未來能加入更多地圖、列車、城市類型、交通模式與事件。

## 1.4 與一般單城捷運模擬的差異

本作以「多城市區域路網」為核心。為保留捷運經營特色，遊戲採用架空的**區域捷運／都會軌道交通公司**設定：玩家負責連接城市、城市群與交通樞紐。初期玩法以城市級車站和城市間路線為主；資料模型必須預留未來在大型城市內增加多個行政區站點、支線和市區捷運線的能力。

不要把遊戲做成純粹的鐵路駕駛遊戲，也不要把它做成只有城市點與收益數字的放置遊戲。

# 2. 核心遊戲循環

整體循環如下：

1. **觀察地圖**：查看城市位置、人口、需求、地形、既有路線與可開發城市。
2. **選擇建設目標**：評估哪些城市值得連接，以及路線應如何繞行。
3. **規劃路線**：選擇起點、途經站點和終點，預覽距離、成本與預估需求。
4. **興建路線**：支付建設費，完成軌道與車站建設。
5. **購買及配置列車**：依路線距離、乘客需求與班距配置車隊。
6. **開始營運**：列車依時刻表自動行駛，乘客依起訖地和網絡可達性搭乘。
7. **檢視經營數據**：查看收入、支出、載客率、等待時間、準點率及滿意度。
8. **調整網絡**：增開班次、延伸路線、增加轉乘、升級車站或更換列車。
9. **擴張公司**：解鎖更多城市與科技，達成章節目標。

要讓玩家能在每一輪循環中做出有意義的決策。不能讓收益只隨時間無條件增加。

# 3. 地圖與世界系統

## 3.1 大型區域地圖

建立一張可縮放、可平移的 2D 區域地圖。地圖上分布多座城市，各城市有固定地理座標和獨立屬性。整體視覺可採用簡潔、略帶插畫感的地圖風格，不需要真實世界 GIS 資料。

地圖至少包含：

- 城市標記與城市名稱。
- 城市規模／人口的視覺差異。
- 城市之間的地理距離。
- 地形區域，例如平原、山區、河流、海岸。
- 已建成路線、施工中路線與可規劃路線。
- 車站、轉乘站和列車位置。
- 地圖圖例、縮放控制和視角重設。

初始畫面應能清楚辨識城市與路網。避免過多裝飾、道路或建築遮住路線。

## 3.2 城市資料

每座城市至少有以下資料：

- 唯一 ID。
- 名稱。
- 地圖座標（x、y，使用地圖世界座標，不直接使用螢幕座標）。
- 人口基數。
- 城市等級／規模。
- 產業組成：住宅、商業、工業、教育、觀光等比例。
- 交通需求倍率。
- 城市成長率。
- 建設難度／地形修正。
- 解鎖狀態。
- 城市發展等級。
- 已連接的車站與路線 ID。

城市不能全部只有名字和人口。至少讓不同城市產生不同的客流特徵。

## 3.3 城市類型

可使用資料參數生成城市類型，例如：

| 城市類型 | 特徵 | 交通需求特點 |
|---|---|---|
| 首府／核心都市 | 人口大、商業與服務業集中 | 全天需求高、轉乘需求高 |
| 工業城市 | 工業與物流活動多 | 工作日通勤明顯 |
| 大學城 | 學校與學生人口較多 | 上下課時段需求集中 |
| 觀光城市 | 景點與旅館多 | 假日、活動期間需求高 |
| 衛星城市 | 居住人口多、工作機會較少 | 通勤往核心都市的需求高 |
| 港口／機場城市 | 具有大型交通樞紐 | 長途旅客和行李客流較多 |
| 小型城鎮 | 人口少、建設成本較低 | 需求較低，但可作為路線中繼站 |

城市類型應由參數驅動，不要將客流結果寫死在城市名稱上。

## 3.4 世界地圖生成

至少提供一張完整、固定 seed 的預設地圖。城市位置應合理分布，避免重疊、全部排成直線或距離差異過小。

建議生成規則：

- 先建立地圖區域與地形遮罩。
- 依指定區域數量生成城市群。
- 城市群內有一座大型核心城市，周圍分布中小型城市。
- 加入少量遠距離城市、山區城市和海岸城市。
- 檢查城市之間的最小距離，避免圖示和標籤重疊。
- 地圖 seed 必須存入存檔，確保載入後世界位置不變。

第一版不需要無限地圖。優先完成一張完整、有多城市、可玩性足夠的區域地圖。後續再支援更多地圖和程序生成。

## 3.5 地圖互動

必須支援：

- 滑鼠拖曳平移地圖。
- 滾輪縮放，並以滑鼠位置作為縮放中心。
- 點擊城市打開城市資訊。
- 點擊路線打開路線資訊。
- 點擊車站查看車站資訊。
- 按住或拖曳時，不應誤觸城市。
- 有明顯的選取、 hover、建設預覽和無效操作狀態。
- 提供「回到整張地圖」按鈕。

地圖使用世界座標，並建立 world-to-screen 與 screen-to-world 轉換。縮放和平移時，路線、城市標記、車站和選取狀態必須保持正確對齊。

# 4. 路線規劃與建設系統（最重要）

## 4.1 設計目標

路線建設是核心玩法。玩家必須自行決定路線的起點、終點和中途停靠城市。系統負責計算建設費、行駛距離、營運時間與預估需求，但不能取代玩家的規劃決定。

## 4.2 路線建設流程

1. 玩家按下「建立路線」。
2. 選擇路線類型及顏色。
3. 點擊地圖上的第一座可用城市，設定起點。
4. 依序點擊其他城市，新增途經站點。
5. 選擇終點，完成路線草稿。
6. 系統顯示路線預覽、距離、建設成本、預估時間、預估客流和可能收益。
7. 玩家可重新排序、刪除或替換途經站點。
8. 確認建設後扣除資金，建立路線及站點連接。
9. 建設完成後才能購買或分配列車並開始營運。

建設模式需要有清晰的取消、返回上一步、清空草稿及確認功能。

## 4.3 路線規則

- 一條路線至少需要兩個不同城市站點。
- 不允許同一站點在同一條簡單路線中連續重複。
- 起點和終點不可相同，除非未來明確支援環狀線。
- 路線每一段都必須有有效距離。
- 不足資金時不能確認建設。
- 路線建立後產生唯一 ID，並記錄城市站點順序。
- 支援路線延伸、支線與未來的環狀線，但第一版先完成一般點到點／多站路線。
- 不同路線可在同一城市交會，該城市可作為轉乘站。
- 同一組城市可以被不同路線連接，但必須有建設成本與競爭／需求上的合理性。

## 4.4 路線幾何

路線的營運拓撲與畫面幾何必須分開：

- **拓撲資料**：路線依序經過哪些城市站點，是模擬與路徑搜尋依據。
- **幾何資料**：地圖上路線實際如何彎曲顯示，是渲染依據。

第一版可讓地圖線段以城市座標連接，並使用平滑曲線或折線避免太僵硬。未來可以加入玩家拖曳控制點調整路線外觀，但不可讓外觀曲線改變站點連接關係。

建設成本以路段的實際世界距離計算，不可使用螢幕像素距離。

## 4.5 路線預覽資訊

建立路線時即時計算：

- 停靠站數。
- 總距離。
- 預估建設成本。
- 預估施工時間（可作為後續版本功能；第一版可立即完工或使用短施工進度）。
- 預估單程時間。
- 經過城市的總人口。
- 起訖點及中途站的潛在客流。
- 路線可能的收入級距。
- 與現有路線的轉乘數量。

預估數據必須清楚標示為估算值，正式營運數據則由實際模擬產生。

## 4.6 路線建設成本

建議使用可調整公式：

`建設成本 = 基礎單位成本 × 路段距離 × 地形倍率 × 建設類型倍率 × 公司科技倍率`

其中：

- 基礎單位成本：遊戲平衡參數。
- 路段距離：相鄰停靠點之間的世界距離總和。
- 地形倍率：平原低、丘陵中、山區高、跨水域最高。
- 建設類型倍率：地面、地下、高架等。
- 公司科技倍率：研究可降低成本，但不可讓成本無限制歸零。

第一版若尚未實作高架／地下選擇，仍須把倍率保留成可擴充設定，不要散落硬編碼。

## 4.7 路線管理

營運後可以：

- 改變路線名稱與顏色。
- 增加或移除停靠站（需要顯示改線影響，並可收取費用）。
- 延長路線。
- 暫停／恢復營運。
- 調整票價（若票價系統已開啟）。
- 調整發車間隔。
- 增加或減少配置列車。
- 查看沿線各站乘降人數。
- 查看路線收入、成本、載客率和準點率。

重大改線不可靜默完成，應先展示受影響的列車和乘客，並要求玩家確認。

# 5. 車站與轉乘系統

## 5.1 城市站點

第一版每座城市至少有一個主要車站。資料模型要預留同一座城市有多個車站的能力，以便後續加入市區內部捷運。

車站資料至少包含：

- ID、名稱、所屬城市 ID。
- 地圖座標。
- 站等級。
- 站點容量。
- 所屬路線 ID 清單。
- 每個時間區間的進站／出站人數。
- 設施等級。
- 乘客滿意度。

## 5.2 轉乘

若兩條或以上路線在同一座車站交會，該站可成為轉乘站。

轉乘會帶來：

- 更廣泛的可達城市範圍。
- 額外乘客流量。
- 轉乘步行時間或懲罰。
- 車站容量壓力。
- 車站升級與維護成本。

乘客路徑搜尋必須把轉乘時間納入成本，不能只計算列車行駛距離。

## 5.3 車站升級

初期升級方向：

- 月台容量：提升可容納乘客量。
- 站體容量：降低尖峰擁擠。
- 轉乘設施：降低轉乘時間。
- 商業設施：增加非票務收入。
- 旅客服務：提高滿意度。

升級需有費用、等級上限和清楚效果說明。

# 6. 列車與車隊系統

## 6.1 列車定位

列車不是單純收藏圖鑑。每一款列車都應有不同的營運定位，玩家需要依路線需求購買及配置。

## 6.2 列車資料

每一種列車型號至少有：

- ID、名稱、製造商／系列名稱（可使用架空品牌）。
- 外觀識別與顏色。
- 購買價格。
- 載客容量。
- 最高速度。
- 加速／減速參數（可抽象化）。
- 能源消耗倍率。
- 每時間單位維護成本。
- 舒適度。
- 解鎖等級或科技需求。

每一列實際擁有的列車還需要：

- 唯一車輛 ID。
- 型號 ID。
- 等級／升級狀態。
- 耐久度。
- 當前位置或路線 ID。
- 行駛方向。
- 當前狀態（待命、行駛、停站、維修）。

## 6.3 車隊管理

玩家可以在車庫購買列車，並將列車指派給路線。

路線配置面板需顯示：

- 已配置列車數。
- 建議列車數。
- 實際班距。
- 預估尖峰運能。
- 乘客需求是否超過運能。
- 每期能源與維護成本。

不要只用「列車越多越好」的設計。過度配置會提高成本，配置不足則會造成候車和擁擠。

## 6.4 自動運行

玩家不需要手動駕駛每一列車。列車依路線、行車方向、班距和時間自動運行。

至少支援：

- 往返營運。
- 站點停靠。
- 乘客上下車。
- 依載客量限制上車。
- 往返端點折返。
- 暫停或恢復列車。
- 維修狀態。

第一版可以採用抽象化的列車位置與運行時間模型，不需要逐個模擬輪子、軌道物理或碰撞。

# 7. 乘客需求與運輸模擬

這個系統必須有實際邏輯，讓路線規劃會影響乘客流量和財務結果。

## 7.1 乘客需求模型

採用 **OD（Origin-Destination，起點－目的地）需求矩陣**，不必為每名乘客建立獨立物件。

每個模擬時間區間，根據城市屬性產生各城市之間的潛在出行需求。

需求可由以下因素決定：

- 起點城市人口。
- 目的地城市人口與工作／商業吸引力。
- 城市類型與產業組成。
- 城市間距離。
- 時段（尖峰、離峰、夜間）。
- 星期或假日。
- 特殊活動事件。
- 現有交通網絡可達性。
- 票價與服務品質。

可先使用重力模型或可調整的啟發式公式：

`OD需求 = 起點產生率 × 起點人口 × 目的地吸引力 ÷ 距離阻抗`

再乘上時段、事件、票價和服務品質等倍率。公式和係數要集中管理，方便測試與平衡。

## 7.2 乘客路徑搜尋

乘客需要從起點城市前往目的地城市。系統在現有交通網絡中搜尋可行路徑。

路徑成本不只看距離，建議納入：

- 車上行駛時間。
- 候車時間。
- 轉乘時間。
- 轉乘次數懲罰。
- 票價成本（可先用權重簡化）。
- 路線擁擠程度。

使用 Dijkstra 或其他適合加權圖的演算法。圖的節點應表示車站，邊表示列車可行駛路段或轉乘連接。

同一 OD 若沒有可行路徑，該需求不能被計入已運送乘客或票務收入。

## 7.3 客流分配

- 依路徑搜尋結果將需求分配到可用路線。
- 每條列車有容量上限。
- 車站月台有容量上限。
- 超過運能的乘客可能等待下一班車。
- 等待過久的部分乘客可以放棄搭乘，形成未滿足需求。
- 乘客乘坐多段路線時，需要正確計算轉乘及上下車。

第一版可使用分批乘客流量（cohort / aggregate flow）模擬，不需要創建大量個別乘客實體。資料必須保留來源、目的地、目前所在線路或候車站等必要資訊，以便正確處理後續路段。

## 7.4 服務品質指標

至少計算：

- 平均候車時間。
- 平均旅程時間。
- 平均轉乘次數。
- 列車載客率。
- 未滿足需求比例。
- 準點率或服務可靠度。
- 乘客滿意度。

這些指標應能回饋到乘客需求、城市成長、聲望或任務評分，但倍率要保守，避免形成無限正向循環。

# 8. 時間與營運模擬

## 8.1 遊戲時間

提供可控制的遊戲時間：

- 暫停。
- 1 倍速度。
- 2 倍速度。
- 4 倍速度。

可依實作能力加入 8 倍速度。速度切換不得改變模擬結果的邏輯順序。

## 8.2 時段

至少有尖峰、一般、離峰和夜間時段。不同時段會影響 OD 需求、建議班距與收入。

## 8.3 固定時間步進

模擬核心使用固定時間步進（fixed timestep），不要直接把畫面每一幀的 delta time 當成經濟計算依據。

建議：

- UI 動畫使用 requestAnimationFrame。
- 模擬核心使用固定 tick，例如每個遊戲分鐘或固定模擬間隔。
- 快轉時增加每秒處理的模擬 tick 數量，而不是讓單次 tick 的邏輯失真。
- 暫停時停止世界模擬，但 UI 動畫仍可運作。
- 頁面切到背景時要有明確策略，避免背景分頁造成巨量補算。

## 8.4 營運報表

提供每日／每週／每月摘要：

- 乘客總量。
- 票務收入。
- 商業收入。
- 列車能源支出。
- 維護支出。
- 車站支出。
- 淨利潤。
- 各路線營運表現。

所有報表應由模擬資料計算，不可顯示固定假數字。

# 9. 經濟系統

## 9.1 貨幣

使用單一主要貨幣即可。第一版不要同時引入太多代幣、材料或付費貨幣。

## 9.2 收入

- 乘客票務收入。
- 車站商店租金。
- 車站廣告收入。
- 章節／任務獎勵。
- 政府或城市建設補助（作為任務獎勵，不應成為永久無條件收入）。

## 9.3 支出

- 路線建設成本。
- 車站建設及升級成本。
- 列車購買成本。
- 列車能源消耗。
- 列車維護成本。
- 車站營運成本。
- 科技研究費。

## 9.4 經濟平衡原則

- 初始資金足以完成第一條短路線和購買基本列車，但不能一次連接大部分城市。
- 短路線容易開始營運，但收入有限。
- 長路線可以連接更多城市，但建設成本、旅行時間和列車需求也更高。
- 經過大型城市不代表一定高獲利，還要考慮城市間實際 OD 需求和路線效率。
- 轉乘可以提升網絡可達性，但車站容量和轉乘成本也會增加。
- 買太多列車會提高固定支出。
- 低需求路線可以虧損，玩家需要調整或暫停。
- 不要讓一條路線因為單一倍率而永久無限賺錢。

所有平衡數值集中在設定資料，不可散落在 UI 或多個系統中。

# 10. 公司成長、解鎖與科技

## 10.1 公司等級

透過運輸乘客、完成路線、完成任務和改善服務取得公司經驗。

公司等級可解鎖：

- 新城市。
- 新列車型號。
- 更多可營運路線數量（若需要限制）。
- 車站升級項目。
- 科技研究。
- 更大型的地圖區域。

不要把所有建設限制都綁在等級上。合理的資金和地理條件也應是主要限制。

## 10.2 科技研究

第一版可提供三條研究線：

1. **列車技術**：容量、速度、能源效率、維護效率。
2. **車站技術**：容量、轉乘效率、商業收入、旅客服務。
3. **營運技術**：調度效率、班次管理、營運成本、需求預測。

每項研究需有成本、前置條件、研究時間或研究點數，以及明確效果。

# 11. 任務與關卡系統

## 11.1 模式

第一版建議包含：

- **生涯／章節模式**：有目標、有初始資源限制，逐步擴張地圖。
- **自由經營模式**：提供較寬鬆的資源和建設限制，讓玩家自由規劃網絡。

若開發時程有限，先完成生涯模式的可玩流程，再加入自由模式。

## 11.2 任務目標

任務可組合以下目標：

- 連接指定城市。
- 在指定數量城市間建立服務。
- 累計運送一定乘客量。
- 達到指定營運收入或淨利潤。
- 達到指定乘客滿意度。
- 將指定路線載客率維持在合理範圍。
- 建立轉乘站。
- 在預算內完成建設。
- 將指定城市的可達性提升到目標。

## 11.3 程序化任務生成

任務目標由規則與地圖狀態生成，不要將每一關完整內容寫死。

任務生成流程：

1. 讀取目前章節、公司等級、已解鎖城市及現有路網。
2. 建立符合進度的目標候選池。
3. 排除目前無法達成或無意義的目標。
4. 選取主要目標與 1 至 2 個附加目標。
5. 依目標生成獎勵與限制。
6. 執行可達性檢查，確認任務在目前地圖和資源條件下可完成。
7. 將任務 seed、目標參數與進度保存，載入後不可重新抽取成不同任務。

程序生成不是無限制隨機。必須有難度評估、可行性檢查與避免重複的機制。

## 11.4 任務評價

可以採用一至三星評價：

- 一星：完成主要目標。
- 二星：完成主要目標並達成一項附加條件。
- 三星：完成全部附加條件或達成更高效率標準。

星級只用於進度和獎勵，不應讓玩家看不懂任務是否完成。

# 12. 隨機事件與城市動態

事件用於改變地圖需求與經營條件，不可只做成無關遊戲的彈出視窗。

事件範例：

- 大型展覽：特定城市短期客流增加。
- 學期開始：大學城通勤需求增加。
- 節慶活動：觀光城市需求增加。
- 新商業區開發：某城市長期吸引力增加。
- 能源價格上升：列車營運成本暫時增加。
- 車站周邊施工：特定車站容量暫時下降。
- 城市人口成長：長期 OD 需求增加。

事件要有發生條件、持續時間、影響範圍、數值倍率和文字說明。事件資料應可擴充。

# 13. UI／UX 與操作設計

## 13.1 整體視覺方向

- 現代、簡潔、清楚、有質感。
- 地圖是最大視覺區域。
- 深色或中性底色皆可，但要確保城市、路線和狀態有足夠對比。
- 使用一致的間距、圓角、字級和圖示規則。
- 避免傳統網頁後台的密集表格感。
- 避免大量浮動視窗同時遮住地圖。
- 路線顏色必須容易區分，且不只依賴顏色辨識，選取路線也要有線寬或外框提示。

## 13.2 主畫面資訊配置

建議採用以下資訊層級：

- **中央／主要區域**：可互動的大型區域地圖。
- **頂部資訊列**：資金、公司等級、遊戲日期、時間速度、暫停。
- **左側或側邊工具列**：選取、建設路線、城市、路線管理、車庫、研究、任務。
- **右側資訊面板**：依目前選取的城市、路線、車站或列車顯示細節。
- **底部狀態列**：重要通知、最近事件或模擬狀態。

在窄螢幕上，側邊面板改為抽屜或底部面板，不可讓地圖完全無法操作。

## 13.3 必要畫面

1. 主選單：新遊戲、繼續遊戲、選擇模式、設定。
2. 區域地圖：遊戲主要操作場景。
3. 城市面板：人口、產業、需求、發展、連接狀況。
4. 路線建設面板：站點順序、距離、成本、預覽和確認。
5. 路線詳情：列車、客流、收入、成本、服務品質。
6. 車庫：列車購買、列車資料、配置路線。
7. 財務面板：收入、支出、淨利和趨勢。
8. 任務面板：主要目標、附加目標、獎勵、進度。
9. 科技面板：研究分支、解鎖條件和效果。
10. 設定：音效、音樂、動畫、速度、資料管理。

## 13.4 互動回饋

- 選取城市時有高亮與資訊面板。
- 建設路線時即時顯示可選站點與路線預覽。
- 不合法的路線要說明原因，而不是單純按鈕失效。
- 資金不足時顯示差額。
- 建設成功時有清楚提示和適度動畫。
- 收入支出發生時要有可查閱的紀錄。
- 任務達成要有明確回饋。

動畫以短、順暢、不干擾操作為原則。提供關閉或降低動畫的選項。

# 14. 音效、動畫與震動

## 14.1 動畫

至少包含：

- 城市 hover／選取狀態。
- 路線建立預覽與確認動畫。
- 列車沿路線移動。
- 車站乘客流量或站點狀態變化。
- 收入數字變動。
- 任務完成和解鎖動畫。
- 面板開關與切換動畫。

列車動畫應以模擬資料中的位置為基礎，不可只在路線上無意義地循環移動。

## 14.2 音效

可選擇加入按鈕、建設完成、列車進站、任務完成等音效。音效管理需集中，能統一調整音量或關閉。

## 14.3 震動

若瀏覽器或裝置支援 Vibration API，可在玩家主動操作後使用短促震動回饋；不支援時必須正常運作，不可造成錯誤。震動須可在設定中關閉。不可在未取得使用者互動前自動要求播放音效或震動。

# 15. 技術規格與建議實作方式

## 15.1 技術基礎

- Vite
- TypeScript（啟用嚴格型別檢查）
- HTML / CSS
- 使用原生 DOM、SVG 或 Canvas 實作地圖；可依效能與現有依賴選擇。
- 不需要一開始引入大型遊戲引擎。
- 若需要狀態管理，選擇輕量且適合現有專案的方式；不可讓 UI 元件成為模擬資料的唯一來源。

## 15.2 地圖渲染建議

優先考慮 SVG 或 Canvas：

**SVG 適合：**
- 城市和車站數量中小型。
- 路線需要清楚的向量線條和互動命中。
- 需要方便做 hover、選取和無障礙標籤。

**Canvas 適合：**
- 地圖物件很多。
- 需要大量列車動畫或頻繁重繪。

可採混合方式：Canvas 負責底圖和大量動畫，DOM/SVG 負責選取、標籤和 UI。第一版以最簡單可靠的方案為主，不要為了架構複雜化而過度工程化。

## 15.3 模組責任

不強制目錄結構，但程式責任至少要分清楚：

- **Game State**：保存玩家、世界、地圖、經濟和模擬狀態。
- **Map Renderer**：只負責地圖繪製與畫面座標轉換。
- **Map Interaction**：處理點擊、拖曳、縮放、選取和建設操作。
- **Route System**：路線建立、編輯、距離、成本和拓撲資料。
- **Passenger Simulation**：OD 需求、路徑搜尋、客流分配、上下車。
- **Train Simulation**：列車位置、班距、停站、折返和容量。
- **Economy System**：收入、支出、現金和財務紀錄。
- **Progression System**：公司等級、解鎖、任務與科技。
- **Event System**：隨機事件及效果。
- **Save System**：序列化、版本管理、讀檔和資料驗證。
- **UI Layer**：畫面顯示與使用者操作，不直接計算核心模擬結果。

## 15.4 資料流原則

- 使用單一、明確的遊戲狀態來源。
- 玩家操作透過明確的 command/action 改變狀態。
- 模擬系統讀取狀態並產生結果。
- UI 訂閱狀態並顯示結果。
- 不可由 UI 元件各自保存一份互相衝突的城市、列車或資金資料。
- 避免直接修改深層資料造成難以追蹤的副作用；可使用明確 reducer、command 或 service。
- 計算結果應可測試，不依賴 DOM 或瀏覽器畫面。

# 17. 重要演算法與資料一致性

## 17.1 城市間距離

使用世界座標計算距離：

`distance(a, b) = sqrt((a.x - b.x)^2 + (a.y - b.y)^2)`

若地圖有不同地形，可對每一段套用地形倍率。螢幕縮放不應影響距離或建設成本。

## 17.2 路線拓撲圖

建立以車站為節點的加權圖：

- 同一路線上相鄰停靠站建立雙向行駛邊（若路線為雙向）。
- 路線交會的同一站點建立轉乘連接。
- 行駛邊權重代表行駛時間。
- 轉乘邊權重代表步行／等待時間與轉乘懲罰。

路線資料變更後，重新建立或增量更新路網圖，避免乘客仍使用已失效路線。

## 17.3 OD 需求

使用可測試的純函式或獨立 service 計算每個模擬區間的 OD 需求。要避免雙重計算同一批需求。

## 17.4 乘客分配

第一版可以分階段實作：

1. 先驗證 OD 起訖城市是否有可行路徑。
2. 將乘客量分配至路徑上的路線和區段。
3. 根據列車容量分配已服務人數。
4. 記錄候車、轉乘、成功運送和放棄的人數。
5. 依實際完成運輸的乘客計算票務收入。

不可把「潛在需求」直接當成「已搭乘人數」。

## 17.5 列車行駛

使用路線的站點順序和每段距離，計算列車每個 tick 的位置。列車必須遵守停站、發車間隔和端點折返規則。

列車在地圖上的位置應由模擬狀態推導，不可以只用 CSS 動畫自行移動而不更新遊戲狀態。

## 17.6 固定 seed

所有程序生成使用可指定 seed 的偽隨機數產生器。不得在各處直接呼叫不可控的 `Math.random()` 來生成會影響遊戲進度的內容。

# 18. 存檔與讀檔系統

## 18.1 基本要求

第一版必須支援本機自動存檔和手動存檔。

- 新遊戲建立獨立存檔。
- 定期自動存檔。
- 重要事件後觸發存檔，例如完成任務、購買列車、建設路線。
- 提供「繼續遊戲」和「新遊戲」入口。
- 有多存檔欄位更好；若第一版只做單一存檔，也必須預留擴充。
- 提供清除存檔功能，但必須二次確認。
- 存檔讀取失敗時顯示可理解錯誤，不可直接讓整個遊戲白屏。

## 18.2 儲存技術

第一版可使用 localStorage 儲存小型存檔；若世界狀態、歷史紀錄和乘客資料變大，改用 IndexedDB。儲存介面要抽象化，讓遊戲邏輯不依賴特定儲存實作。

不得每一幀都寫入存檔。採用 debounce、固定週期和重要事件觸發。

## 18.3 存檔內容

至少儲存：

- 存檔版本。
- 地圖 seed 和世界資料。
- 玩家資金、等級、科技和進度。
- 城市解鎖及發展狀態。
- 路線、車站和路線幾何資料。
- 車庫列車與車隊配置。
- 列車當前狀態和位置。
- 遊戲時間與速度（載入時可預設暫停）。
- 乘客流量與必要的候車批次。
- 財務紀錄摘要。
- 目前任務和任務 seed／進度。
- 進行中的事件。
- 使用者設定。

## 18.4 版本遷移

存檔需有 `saveVersion`。載入時驗證資料、補上新版本預設欄位，並對無法修復的資料提供錯誤訊息。不得假設 localStorage 中永遠只有最新版本資料。

## 18.5 匯出與匯入

建議提供 JSON 存檔匯出／匯入，方便備份和測試。匯入時必須驗證 schema、版本與數值範圍，不能直接信任使用者提供的 JSON。

# 19. 效能與穩定性

- 不要為每名乘客建立獨立 DOM 節點。
- 大量城市、站點和路線應避免每 tick 重新建立全部 UI。
- 地圖渲染與模擬邏輯分離。
- 模擬採固定 tick，渲染採 requestAnimationFrame。
- 使用適當的快取，但必須有失效策略；路網變更時要更新路徑快取。
- 只更新必要的 UI 區域。
- 避免每次滑鼠移動都觸發完整遊戲狀態重算。
- 對路線建設、路徑搜尋和乘客分配加入合理的資料量上限或分批處理。
- 遊戲切換到背景或重新載入時，必須保持資料一致。

第一版的效能目標：在一般桌面瀏覽器中，數十座城市、數百個站點／路段規模下，地圖操作保持順暢，正常遊戲速度不應出現明顯卡頓。若測試設備不足，需記錄實測規模和瓶頸，不要宣稱未測試的效能數字。

# 20. 測試與驗收標準

## 20.1 功能驗收

- [ ] 能建立新遊戲並產生固定 seed 的多城市地圖。
- [ ] 城市位置、名稱和屬性在重新載入後保持一致。
- [ ] 地圖能平移、縮放、點選城市。
- [ ] 能從城市站點建立一條至少兩站的自訂路線。
- [ ] 建設前能看到距離和成本預覽。
- [ ] 資金不足時無法建設，且有明確提示。
- [ ] 建設完成後路線正確顯示在地圖上。
- [ ] 能購買列車並分配到路線。
- [ ] 列車能依路線自動往返運行。
- [ ] 城市之間會產生 OD 乘客需求。
- [ ] 乘客只會被計入實際可達且成功運輸的流量。
- [ ] 列車容量會限制實際載客量。
- [ ] 轉乘路線能讓乘客完成跨路線旅程。
- [ ] 收入與成本會依實際營運結果更新。
- [ ] 能檢視路線營運數據與公司財務。
- [ ] 能完成至少一種任務並取得獎勵。
- [ ] 自動存檔有效，重新整理後可以繼續遊玩。
- [ ] 手動存檔、讀檔和清除存檔有效。
- [ ] 沒有明顯無作用的按鈕或純展示面板。

## 20.2 演算法測試

至少測試以下情境：

1. 兩城市之間只有一條路線：乘客能正確抵達。
2. 起點與終點無連線：不應產生已服務乘客或票務收入。
3. 兩條路線在同一車站交會：乘客可轉乘。
4. 有兩條可行路徑：能依加權成本選擇合理路徑。
5. 列車容量不足：未服務乘客應等待或流失，不可超載。
6. 玩家刪除或修改路線：舊路徑快取失效，乘客不再走失效路線。
7. 建設成本計算：地圖縮放和平移不影響成本。
8. 固定 seed：同一 seed 產生一致的地圖及初始任務。
9. 快轉及暫停：模擬結果不因渲染幀率而錯亂。
10. 存檔往返：存檔、載入後的資金、路線、列車和時間狀態一致。

## 20.3 品質驗收

- TypeScript strict 檢查通過。
- Vite production build 成功。
- 沒有未處理的 console error。
- 沒有因資料不存在而造成的白屏。
- 主要 UI 可在桌面和窄螢幕使用。
- 所有重要操作有成功或失敗回饋。
- 存檔格式有版本欄位和基本驗證。

# 22. 第一版範圍控制（MVP）

為避免專案過度膨脹，第一個可交付版本必須聚焦以下內容：

### MVP 必須有

- 一張包含約 20 至 30 座城市的區域地圖。
- 城市有不同人口、類型和需求。
- 玩家可自行規劃多站路線。
- 路線建設成本與資金限制。
- 至少 3 種可購買列車型號。
- 列車自動往返營運。
- 基本 OD 乘客需求與路徑搜尋。
- 列車容量及候車限制。
- 票務收入與營運成本。
- 至少 5 種可生成的任務目標。
- 本機自動存檔與繼續遊戲。
- 完整且可操作的主畫面與管理面板。

### MVP 可以先簡化

- 施工時間可先簡化為建設確認後立即完成。
- 列車物理可用抽象時間模型。
- 城市內多站系統可以先保留資料模型，第一版先以每城一個主要站點遊玩。
- 事件先做少量但有效的事件。
- 科技樹先做少量明確效果。
- 乘客以群組流量模擬，不建立個別乘客角色。

### MVP 不要做

- 真實世界地圖 API 或線上地圖服務依賴。
- 多人連線或即時 PvP。
- 真實列車物理和駕駛操作。
- 複雜 3D 城市建模。
- 付費商城、抽卡或廣告系統。
- 大量裝飾性 UI 卻沒有真正模擬功能。
- 一開始就製作無限地圖。

完成後請提供：

1. 可直接啟動的 Vite + TypeScript 遊戲。
2. 完整且可玩的核心循環，不是靜態 Demo。
3. 可互動的多城市區域地圖。
4. 真正由玩家規劃的路線建設系統。
5. 可運行的列車、乘客、經濟與成長系統。
6. 穩定的本機存檔與讀檔。
7. 清楚的操作提示和新手引導。
8. 已通過的型別檢查、測試與 production build。
9. 簡短的操作說明：如何開始遊戲、建設路線、購買列車、開始營運和存檔。
10. 已知限制清單：只列出確實尚未實作或刻意簡化的項目，不可把未完成項目描述成已完成。

**最重要的驗收原則：打開遊戲後，玩家看到的是一張有許多城市的大型地圖；玩家能親自決定先連接哪幾座城市、路線經過哪些城市，以及如何配置列車。建立的網絡必須真的運作，乘客會依照網絡移動，營運結果會反映玩家的規劃。這才是本作的核心，不可偏離。**
